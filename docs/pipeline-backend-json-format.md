# JSON-контракт пайплайнов

Текущая версия: **0.2** (включая необязательные настройки окружения Python). Источник транспортных моделей —
[typespec/main.tsp](../typespec/main.tsp); OpenAPI генерируется в
[api/openapi.yaml](../api/openapi.yaml). Frontend пока использует локальный
mock-репозиторий в режиме `?mock=true`. По умолчанию сохранено подключение к
HTTP API из main: каталог, чтение/сохранение/сброс/проверка черновика и публикация.
Модели расположены в `typespec/models/`, операции — в `typespec/operations/`.
Расширения 0.2 и исполнение Python требуют отдельной backend-интеграции;
в этой frontend-доработке серверный Go-код не меняется.

## 1. Каталог, пайплайн, ревизия и черновик

Каталог-папка: `{ id, parentId: string | null, name }` объединяет пайплайны
и вложенные каталоги. Это отдельная сущность от каталога типов кубиков.

Пайплайн: `{ id, folderId, name, currentRevision: number | null }`.
Ревизия: `{ pipelineId, revision, definition }` — неизменяемый опубликованный
граф. Номер ревизии положительный, последовательный в пределах пайплайна.

Черновик: `{ pipelineId, baseRevision: number | null, definition }`.
Он изменяемый, один на пайплайн, не имеет номера ревизии и не запускается.
`baseRevision` сохраняется при редактировании, но не защищает от конкурирующего
сохранения двух вкладок: при HTTP-интеграции нужен ETag или draftVersion.

## 2. Канонический граф

Пример: входной файл → пользовательский Python-кубик → консоль → return.

```json
{
  "schemaVersion": "0.2",
  "nodeCatalogVersion": "0.2",
  "inputs": {
    "sourceFile": {
      "type": "artifact.file",
      "title": "Исходный файл",
      "required": true
    }
  },
  "nodes": [
    {
      "id": "input-file",
      "type": "builtin.file-input",
      "typeVersion": 1,
      "title": "Загруженный файл",
      "config": {
        "inputName": "sourceFile"
      },
      "ui": {
        "position": {
          "x": 80,
          "y": 180
        }
      }
    },
    {
      "id": "python-read",
      "type": "builtin.python",
      "typeVersion": 1,
      "title": "Обработать файл",
      "config": {},
      "inputs": [
        {
          "name": "file",
          "title": "Файл",
          "dataType": "artifact.file",
          "minConnections": 1,
          "maxConnections": 1
        }
      ],
      "outputs": [
        {
          "name": "text",
          "title": "Текст",
          "dataType": "text"
        }
      ],
      "implementation": {
        "language": "python",
        "entrypoint": "run",
        "code": "def run(inputs):\n    # Runner передаст artifact.file как локальный путь\n    with open(inputs[\"file\"], encoding=\"utf-8\") as source:\n        text = source.read()\n    print(f\"Прочитано символов: {len(text)}\")\n    return {\"text\": text}\n",
        "pythonVersion": "3.12",
        "requirements": []
      },
      "ui": {
        "position": {
          "x": 380,
          "y": 180
        }
      }
    },
    {
      "id": "print-text",
      "type": "builtin.console-print",
      "typeVersion": 2,
      "title": "Вывести в консоль",
      "config": {
        "prefix": ""
      },
      "ui": {
        "position": {
          "x": 680,
          "y": 180
        }
      }
    },
    {
      "id": "return",
      "type": "builtin.return",
      "typeVersion": 1,
      "title": "return",
      "config": {},
      "inputs": [
        {
          "name": "in",
          "title": "Вход",
          "dataType": "any",
          "minConnections": 1,
          "maxConnections": null
        }
      ],
      "outputs": [
        {
          "name": "result",
          "title": "Результат",
          "dataType": "any",
          "sourcePort": "in"
        }
      ],
      "ui": {
        "position": {
          "x": 980,
          "y": 180
        }
      }
    }
  ],
  "edges": [
    {
      "id": "edge-input-read",
      "source": {
        "nodeId": "input-file",
        "port": "file"
      },
      "target": {
        "nodeId": "python-read",
        "port": "file"
      }
    },
    {
      "id": "edge-read-print",
      "source": {
        "nodeId": "python-read",
        "port": "text"
      },
      "target": {
        "nodeId": "print-text",
        "port": "text"
      }
    },
    {
      "id": "edge-print-end",
      "source": {
        "nodeId": "print-text",
        "port": "done"
      },
      "target": {
        "nodeId": "return",
        "port": "in"
      }
    }
  ],
  "ui": {
    "viewport": {
      "x": 0,
      "y": 0,
      "zoom": 0.82
    }
  }
}
```

| Поле графа | Значение |
| --- | --- |
| `schemaVersion` | `"0.2"`, структура документа |
| `nodeCatalogVersion` | `"0.2"`, версия каталога типов |
| `inputs` | Объявления входов запуска, словарь по имени |
| `nodes` | Экземпляры кубиков с уникальными `id` |
| `edges` | Связи с уникальными `id` |
| `ui` | Необязательные viewport и расширения визуального редактора |

Порядок `nodes` и `edges` не определяет порядок исполнения DAG. Позиции и
viewport также не влияют на исполнение. React Flow поля `selected`, `measured`,
`sourceHandle` и `targetHandle` в JSON не попадают.

Вход запуска: `{ type, title, required }`. В текущем mock-примере `sourceFile`
имеет тип `artifact.file`. Значение при запуске — идентификатор загруженного
артефакта; содержимое файла, base64 и локальный путь пользователя в графе не
хранятся. Настройки runtime inputs в UI остаются будущей задачей.

## 3. Каталог типов

Каталог: `{ catalogVersion, nodeTypes: NodeTypeDefinition[] }`.
Тип: `{ type, version, title, description?, category, status, inputs, outputs,
configSchema, editablePorts?, implementation? }`.

Пара `type + version` определяет контракт типа; опубликованная пара неизменяема.
Встроенные типы используют `builtin.*`, сторонние могут использовать своё
пространство имён. `active` позволяет создавать и запускать экземпляры;
`deprecated` сохраняет запуск старых экземпляров; `disabled` запрещает запуск.

`editablePorts: true` разрешает экземпляру объявить свои `inputs` и `outputs`.
Отсутствующее поле наследует порты каталога; пустой массив означает отсутствие
портов. У фиксированных типов переопределение портов является ошибкой запуска.
`implementation` в каталоге — шаблон для новых экземпляров, а не скрытая
подстановка при загрузке старого документа.

`configSchema` использует подмножество JSON Schema Draft 2020-12: object,
properties, required, additionalProperties; поля string, number, integer,
boolean; метаданные title, description, default, enum. Frontend строит форму
по этой схеме. Валидация не дописывает defaults в существующий документ.

## 4. Экземпляр кубика

Обязательные поля: `id`, `type`, `typeVersion`, `config`.
Необязательные: `title`, `inputs`, `outputs`, `implementation`, `ui`.
`id` стабилен при перемещении и настройке; `title` — имя экземпляра.
`config` проверяется по схеме типа. `ui.position` — `{ x, y }`.
Неизвестные типы сохраняются в черновике, но блокируют запуск.

### Порт

```json
{
  "name": "text",
  "title": "Текст",
  "dataType": "text",
  "minConnections": 1,
  "maxConnections": null
}
```

Имена уникальны внутри каждого направления и соответствуют
`^[A-Za-z_][A-Za-z0-9_]*$`. Вход и выход могут иметь одинаковое имя.
`title` и `dataType` — непустые строки. Типы: `artifact.file`, `text`,
`number`, `boolean`, `json`, `control` и расширяемые строковые идентификаторы.
Вход `any` принимает любой тип; у обычных выходов нужен конкретный тип.
Выход результата return может иметь `any`, если таков его вход-источник.

Ограничения связей действуют для входов:

| min | max | Значение для Python |
| --- | --- | --- |
| 0 | 1 | Значение или `None`, если не подключён |
| 1 | 1 | Ровно одно значение |
| 0 | null / отсутствует | Список, возможно пустой |
| 1 | null / отсутствует | Непустой список |
| N | M > 1 | Список длины от N до M |

Отсутствующий минимум равен нулю. Границы — целые неотрицательные числа;
конечный максимум не меньше минимума. Для множественного входа значение всегда
список, даже при одной связи. Порядок элементов определяется лексикографической
сортировкой входящих связей по `edge.id`, независимо от порядка в JSON.
Эту семантику должен реализовать будущий backend runner.

## 5. Связи

Связь: `{ id, source: { nodeId, port }, target: { nodeId, port } }`.
Источник — выход кубика, цель — вход. Разрешены несколько источников у одного
пина и несколько разных входов у кубика. Типы должны совпадать, либо целевой
тип должен быть `any`. Полные дубликаты, превышение maxConnections, петли и
циклы запрещены. Разветвление одного выхода на несколько целей разрешено.

Для разветвления создаются несколько обычных связей с одинаковым
`source.nodeId + source.port` и разными целями. Лимита исходящих связей нет;
`maxConnections` ограничивает только вход назначения. Каждая ветка получает
одно и то же значение выхода (для файла — тот же файловый артефакт), а не часть
данных. Разбиение содержимого файла при необходимости описывается Python-кодом.

Например, `input-file.file → python-a.file` и
`input-file.file → python-b.file`: после готовности файла обе операции могут
выполняться параллельно, если остальные их зависимости также готовы. Порядок
связей не задаёт последовательность веток. Этот порядок исполнения должен
обеспечить будущий backend runner; текущий UI только описывает DAG.

Связь означает передачу значения и зависимость выполнения. `control` передаёт
только завершение операции. Переименование порта через UI обновляет связанные
endpoints; удаление порта удаляет его связи. Смена типа или лимита сохраняет
связи для исправления пользователем; проверка покажет несовместимость.

## 6. Текущие типы

| Тип | Версия | Назначение |
| --- | --- | --- |
| `builtin.file-input` | 1 | Файловый вход, config.inputName ссылается на inputs графа; выход file: artifact.file |
| `builtin.python` | 1 | Свой код, редактируемые входы и выходы |
| `builtin.console-print` | 2 | text: text принимает одну или больше связей; печатает каждую строку с config.prefix, выход done: control |
| `builtin.return` | 1 | Завершение pipeline, редактируемые входы и результаты |

`builtin.read-file` удалён из текущего каталога. Чтение файла можно описать
Python-кодом. `builtin.end` заменён на `builtin.return`.

### Python

```json
{
  "language": "python",
  "entrypoint": "run",
  "code": "def run(inputs):\n    print(inputs[\"text\"])\n    return {\"result\": inputs[\"text\"]}\n",
  "pythonVersion": "3.12",
  "requirements": []
}
```

Поле `implementation` обязательно у экземпляра `builtin.python`.

| Поле implementation | Обязательное | Семантика |
| --- | --- | --- |
| `language` | да | `python` |
| `entrypoint` | да | `run` |
| `code` | да | Исходный Python-код с функцией run(inputs) |
| `pythonVersion` | нет | Запрашиваемая версия `3.x` или `3.x.y`; при отсутствии — `3.12` |
| `requirements` | нет | Массив прямых зависимостей; при отсутствии — пустой массив |

### Окружение и зависимости Python

```json
{
  "language": "python",
  "entrypoint": "run",
  "pythonVersion": "3.13",
  "requirements": ["requests==2.32.5"],
  "code": "import requests\n\ndef run(inputs):\n    return {\"result\": requests.__version__}\n"
}
```

В этом примере выход `result` должен иметь тип `text`.
Стандартные модули (`json`, `math`, `datetime`, `collections` и т. п.)
импортируются в коде и в requirements не добавляются. Пакет дистрибутива и имя
импортируемого модуля могут различаться; frontend не выводит зависимости из
import автоматически.

Для MVP принят ограниченный формат зависимостей:

- `package==version`, например `requests==2.32.5`;
- необязательные extras без пробелов: `requests[socks]==2.32.5`;
- версия в канонической записи: числовой release, необязательные epoch,
  `aN`/`bN`/`rcN`, `.postN`, `.devN`, `+local`;
- имена дистрибутивов/extra содержат буквы ASCII, цифры, `.`, `_`, `-`,
  начинаются и заканчиваются буквой или цифрой;
- дубликаты одного дистрибутива запрещены, включая разные extras/версии.
  При сравнении регистр игнорируется, группы `-`, `_`, `.` заменяются на `-`.
  Нужные extras одного пакета следует объединять в одну запись.

Это подмножество [спецификации зависимостей Python](https://packaging.python.org/en/latest/specifications/dependency-specifiers/),
а не произвольный requirements.txt. Незакреплённые версии, диапазоны, wildcard,
URL, локальные пути, environment markers и параметры pip не входят в этот
frontend-контракт. UI принимает по одной записи в строке, обрезает внешние
пробелы и пропускает пустые строки; в JSON сохраняется массив строк.

Frontend проверяет форму версии, синтаксис записей и дубликаты. Он не обращается
к PyPI, не устанавливает пакеты, не проверяет существование релиза, доступность
версии Python, совместимость библиотек или import. Ошибки окружения показываются
в настройках и при проверке графа (`INVALID_PYTHON_VERSION`,
`INVALID_PYTHON_REQUIREMENTS`, `DUPLICATE_PYTHON_REQUIREMENT`). Незавершённый
черновик можно сохранять с такими ошибками для дальнейшего исправления.

`requirements` содержит только намерение пользователя о прямых зависимостях,
а не полный lockfile. Разрешение транзитивных зависимостей, фиксация точных
версий/хешей, подготовка контейнера, установка, кэширование и логи установки —
обязанности будущего backend runner. Исполнение не реализовано в текущем
frontend; код Go и сервисы backend в этой доработке не изменяются.

Поля необязательные и обратно совместимы с документами 0.2 без окружения:
при загрузке и сериализации отсутствующие поля не дописываются автоматически.
UI показывает значение версии по умолчанию. У новых Python-кубиков шаблон
содержит `pythonVersion: "3.12"` и `requirements: []`. Изменение окружения
сохраняет код; изменение кода сохраняет окружение. Отдельной миграции и смены
schemaVersion/nodeCatalogVersion/typeVersion для этого расширения не требуется.

### Вызов Python-кода

`run(inputs)` принимает словарь по именам входов и возвращает словарь по
именам объявленных выходов. Ключи возвращаемого словаря должны соответствовать
объявленным выходам, а значения — их типам. Возврат и Python-синтаксис должен
проверять runner; frontend проверяет только наличие непустого кода и структуру
описания. Переименование порта не переписывает пользовательский Python-код.

Будущий runner материализует `artifact.file` в локальный путь в контейнере
кубика до вызова функции. Этот путь существует только во время запуска.
`print()` попадает в stdout; исключения и stderr — в логи попытки, статус
операции становится Failed. Код не исполняется в браузере. Настройки окружения описаны выше;
подготовка образа, установка зависимостей и изоляция исполнения остаются задачами backend.

### Return

В запускаемом графе ровно один `builtin.return`. Каждый узел должен иметь путь
к нему, и сам return должен иметь хотя бы одну входящую связь. Исходящие связи
запрещены: выходные пины показывают результаты всего pipeline.

Каждый выход return содержит `sourcePort` — имя его входа. Например:

```json
{
  "name": "answer",
  "title": "Ответ",
  "dataType": "text",
  "sourcePort": "text"
}
```

Тип результата совпадает с типом входа. Значение входа (включая список при
множественном подключении) возвращается под именем выхода. Выходы можно
добавлять, переименовывать и удалять; пустой список результатов допустим.
Переименование входа обновляет sourcePort. После удаления входа пользователь
должен удалить или переназначить связанные результаты, иначе запуск невалиден.

## 7. Логи

Логи относятся к конкретному запуску, кубику и попытке; не входят в definition.
Контракт репозитория: `getNodeLogs(runId, nodeId): Promise<NodeLogs | null>`.
`null` означает отсутствие логов. Для будущего HTTP-адаптера транспортная
модель определена в TypeSpec:

```json
{
  "runId": "demo-run-001",
  "nodeId": "python-read",
  "attempt": 1,
  "status": "Succeeded",
  "entries": [
    {
      "timestamp": "2026-11-15T09:00:01Z",
      "stream": "stdout",
      "message": "Прочитано символов: 18"
    }
  ]
}
```

Статус: Succeeded, Failed или Running. stream: stdout или stderr. timestamp —
UTC ISO 8601. Панель отображает loading, error с повтором, пустое состояние
и записи обоих потоков. В текущем frontend есть только явно обозначенный
демонстрационный запуск `demo-run-001`; новые кубики не имеют логов.
Редактирование кода не меняет демонстрационные логи и не запускает исполнение.

## 8. Валидация, сохранение, версии

Черновик можно сохранить с неизвестными типами, незаполненным кодом,
неподключёнными портами или без return. Структура JSON и уникальность id —
требования к будущему серверному сохранению. LocalPipelineRepository сейчас
сохраняет модель локально и не является авторитетным серверным валидатором.

Проверка готовности дополнительно проверяет версии, наличие типов,
configSchema, объявления портов, реализацию Python, endpoints и типы связей,
лимиты, отсутствие дубликатов и циклов, return и достижимость return.
Результат: `{ valid, issues: [{ code, message, location }] }`.
Location содержит kind (graph/node/port/edge/config) и подходящие nodeId,
edgeId, port или configPath (JSON Pointer). Ошибки кликабельны в UI.

Три независимые версии: schemaVersion документа, nodeCatalogVersion каталога,
typeVersion типа кубика. Новые типы выпускаются в новом каталоге; изменение
поведения существующего типа требует новой typeVersion. Поэтому
console-print в каталоге 0.2 имеет версию 2 с множественным входом.

Документы 0.1 автоматически обновляются при загрузке: end → return,
read-file → Python с прежними портами file/text, console-print v1 → v2.
ID, связи, позиции и неизвестные узлы сохраняются; конфигурация
read-file.encoding переносится в код. Результат сразу записывается в
localStorage и загружается в редактор без несохранённых изменений.
Исходный JSON сохраняется под ключом исходного черновика с суффиксом
`:backup:0.1`; существующая резервная копия не перезаписывается.
При ошибке миграции или записи исходный черновик не удаляется, редактор
показывает ошибку загрузки. Документы 0.2 повторно не преобразуются;
неизвестные версии автоматически не обновляются.
