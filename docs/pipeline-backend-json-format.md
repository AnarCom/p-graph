# JSON-контракт пайплайнов

## 1. Каталог, пайплайн и ревизия

### Каталог-папка

Каталог объединяет пайплайны и другие каталоги в древовидную структуру.

```json
{
  "id": "folder-training",
  "parentId": null,
  "name": "Обучение моделей"
}
```

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `id` | да | Стабильный идентификатор каталога. |
| `parentId` | да | Идентификатор родительского каталога; `null` для корневого. |
| `name` | да | Название каталога. |

Каталог-папка не связан с каталогом типов узлов, описанным ниже.

### Пайплайн

Пайплайн — именованная сущность, объединяющая последовательные версии одного
графа.

```json
{
  "id": "pipeline-print-file",
  "folderId": "folder-training",
  "name": "Прочитать и напечатать файл",
  "currentRevision": 3
}
```

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `id` | да | Стабильный идентификатор пайплайна. |
| `folderId` | да | Каталог-папка, в котором находится пайплайн. |
| `name` | да | Название пайплайна. |
| `currentRevision` | да | Номер актуальной ревизии; `null`, пока у нового пайплайна нет ни одной ревизии. |

### Ревизия пайплайна

Ревизия — неизменяемая зафиксированная версия определения графа. Изменения
сначала сохраняются в черновике. При фиксации готового черновика создаётся
ревизия с новым номером.

```json
{
  "pipelineId": "pipeline-print-file",
  "revision": 3,
  "definition": {
    "schemaVersion": "0.1",
    "nodeCatalogVersion": "0.1",
    "inputs": {},
    "nodes": [],
    "edges": []
  }
}
```

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `pipelineId` | да | Идентификатор пайплайна. |
| `revision` | да | Положительный последовательный номер ревизии. |
| `definition` | да | Определение графа в каноническом формате. |

### Черновик пайплайна

Черновик — изменяемое определение графа, которое ещё не стало ревизией. У
пайплайна может быть не более одного черновика.

```json
{
  "pipelineId": "pipeline-print-file",
  "baseRevision": 3,
  "definition": {
    "schemaVersion": "0.1",
    "nodeCatalogVersion": "0.1",
    "inputs": {},
    "nodes": [],
    "edges": []
  }
}
```

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `pipelineId` | да | Идентификатор пайплайна. |
| `baseRevision` | да | Ревизия, на основе которой создан черновик; `null` для нового пайплайна. |
| `definition` | да | Изменяемое определение графа в каноническом формате. |

`baseRevision` не меняется при сохранении черновика. Поле позволяет определить,
что после начала редактирования у пайплайна появилась новая актуальная ревизия.
Черновик не имеет собственного номера ревизии и не может быть запущен.

## 2. Канонический JSON графа

Пример описывает пайплайн:

```text
входной файл -> чтение файла -> вывод текста -> конец
```

```json
{
  "schemaVersion": "0.1",
  "nodeCatalogVersion": "0.1",
  "inputs": {
    "sourceFile": {
      "type": "artifact.file",
      "title": "Исходный файл",
      "required": true
    }
  },
  "nodes": [
    {
      "id": "input-file",
      "type": "builtin.file-input",
      "typeVersion": 1,
      "title": "Загруженный файл",
      "config": {
        "inputName": "sourceFile"
      },
      "ui": {
        "position": {
          "x": 80,
          "y": 160
        }
      }
    },
    {
      "id": "read-file",
      "type": "builtin.read-file",
      "typeVersion": 1,
      "title": "Прочитать файл",
      "config": {
        "encoding": "utf-8"
      },
      "ui": {
        "position": {
          "x": 380,
          "y": 160
        }
      }
    },
    {
      "id": "print-text",
      "type": "builtin.console-print",
      "typeVersion": 1,
      "title": "Вывести в консоль",
      "config": {
        "prefix": ""
      },
      "ui": {
        "position": {
          "x": 680,
          "y": 160
        }
      }
    },
    {
      "id": "end",
      "type": "builtin.end",
      "typeVersion": 1,
      "title": "Конец",
      "config": {},
      "ui": {
        "position": {
          "x": 980,
          "y": 160
        }
      }
    }
  ],
  "edges": [
    {
      "id": "edge-input-read",
      "source": {
        "nodeId": "input-file",
        "port": "file"
      },
      "target": {
        "nodeId": "read-file",
        "port": "file"
      }
    },
    {
      "id": "edge-read-print",
      "source": {
        "nodeId": "read-file",
        "port": "text"
      },
      "target": {
        "nodeId": "print-text",
        "port": "text"
      }
    },
    {
      "id": "edge-print-end",
      "source": {
        "nodeId": "print-text",
        "port": "done"
      },
      "target": {
        "nodeId": "end",
        "port": "in"
      }
    }
  ],
  "ui": {
    "viewport": {
      "x": 0,
      "y": 0,
      "zoom": 1
    }
  }
}
```

## 3. Каталог типов узлов

Описание пайплайна хранит экземпляры узлов, но не дублирует полное описание
каждого типа. Доступные типы находятся в отдельном расширяемом каталоге.

Поле `nodeCatalogVersion` в графе указывает версию каталога, относительно
которой интерпретируются `type`, `typeVersion`, порты и конфигурация узлов.

```json
{
  "catalogVersion": "0.1",
  "nodeTypes": [
    {
      "type": "builtin.text-uppercase",
      "version": 1,
      "title": "В верхний регистр",
      "description": "Преобразует входной текст в верхний регистр",
      "category": "text",
      "status": "active",
      "inputs": [
        {
          "name": "text",
          "title": "Текст",
          "dataType": "text",
          "minConnections": 1,
          "maxConnections": 1
        }
      ],
      "outputs": [
        {
          "name": "text",
          "title": "Результат",
          "dataType": "text"
        }
      ],
      "configSchema": {
        "$schema": "https://json-schema.org/draft/2020-12/schema",
        "type": "object",
        "properties": {
          "locale": {
            "type": "string",
            "title": "Локаль",
            "default": "ru-RU"
          }
        },
        "additionalProperties": false
      }
    }
  ]
}
```

### Контракт типа узла

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `type` | да | Уникальное машинное имя типа. |
| `version` | да | Версия контракта и поведения типа. |
| `title` | да | Человекочитаемое название типа. |
| `description` | нет | Краткое описание поведения. |
| `category` | да | Логическая группа, например `files` или `text`. |
| `status` | да | `active`, `deprecated` или `disabled`. |
| `inputs` | да | Список входных портов. |
| `outputs` | да | Список выходных портов. |
| `configSchema` | да | JSON Schema объекта `config`. |

Пара `type + version` однозначно определяет контракт узла. Уже опубликованное
описание этой пары неизменяемо.

Имена встроенных типов используют пространство `builtin.*`. Для внешних
расширений рекомендуется отдельное пространство имён, например
`acme.training-model`, чтобы типы разных поставщиков не конфликтовали.

Статусы имеют следующую семантику:

| Статус | Новые экземпляры | Запуск существующих экземпляров |
| --- | --- | --- |
| `active` | разрешены | разрешён |
| `deprecated` | не рекомендуются | разрешён |
| `disabled` | запрещены | запрещён |

### Контракт порта

```json
{
  "name": "text",
  "title": "Текст",
  "dataType": "text",
  "minConnections": 1,
  "maxConnections": 1
}
```

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `name` | да | Стабильное машинное имя порта внутри типа узла. |
| `title` | да | Отображаемое название. |
| `dataType` | да | Тип передаваемого значения. |
| `minConnections` | для входа | Минимальное количество входящих связей. |
| `maxConnections` | для входа | Максимальное количество входящих связей; `null` означает отсутствие ограничения. |

Ограничения задаются только для входных портов:

| `minConnections` | `maxConnections` | Допустимое количество связей |
| --- | --- | --- |
| `0` | `1` | Ноль или одна. |
| `1` | `1` | Ровно одна. |
| `0` | `null` | Любое количество. |
| `1` | `null` | Одна или больше. |

`dataType` является строковым идентификатором, поэтому новые типы данных можно
добавлять без изменения общего формата. В MVP используются:

- `artifact.file` — ссылка на загруженный файл;
- `text` — строка;
- `control` — сигнал о завершении узла без пользовательских данных.

На первом этапе выход совместим со входом, если их `dataType` совпадают.

### Конфигурация узла

`configSchema` использует JSON Schema Draft 2020-12. Она описывает допустимое
содержимое `config` у экземпляра узла.

В версии контракта `0.1` поддерживается ограниченное подмножество JSON Schema:

- объект: `type: "object"`, `properties`, `required`,
  `additionalProperties`;
- поля: `type: "string"`, `"number"`, `"integer"` или `"boolean"`;
- метаданные поля: `title`, `description`, `default` и `enum`.

Это позволяет однозначно построить форму настройки узла. Остальные возможности
JSON Schema не входят в контракт версии `0.1`.

Например, описание типа:

```json
{
  "type": "builtin.text-uppercase",
  "version": 1,
  "configSchema": {
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "properties": {
      "locale": {
        "type": "string",
        "default": "ru-RU"
      }
    },
    "additionalProperties": false
  }
}
```

разрешает сохранить экземпляр:

```json
{
  "id": "uppercase-1",
  "type": "builtin.text-uppercase",
  "typeVersion": 1,
  "title": "Нормализовать текст",
  "config": {
    "locale": "ru-RU"
  },
  "ui": {
    "position": {
      "x": 500,
      "y": 200
    }
  }
}
```

### Добавление нового типа узла

Чтобы добавить новый тип:

1. Выбрать уникальное имя `type` и начальную `version: 1`.
2. Добавить описание типа, его порты и `configSchema` в каталог.
3. Выпустить следующую `catalogVersion` с новым описанием.

Формат пайплайна при этом не меняется. В его `nodes` появляется обычный
экземпляр с новым значением `type`, а `nodeCatalogVersion` указывает версию
каталога, содержащую этот тип.

Если меняются порты, конфигурация или поведение существующего типа, создаётся
следующая версия этого типа. Старые пайплайны продолжают ссылаться на старую
версию.

## 4. Поля графа

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `schemaVersion` | да | Версия общего формата документа. |
| `nodeCatalogVersion` | да | Версия каталога типов узлов. |
| `inputs` | да | Входные значения, которые пользователь передаёт при запуске. |
| `nodes` | да | Блоки пайплайна. |
| `edges` | да | Направленные связи между портами блоков. |
| `ui` | нет | Данные визуального редактора, не влияющие на исполнение. |

## 5. Входы пайплайна

`inputs` объявляет значения, необходимые конкретному запуску. В описании
пайплайна хранится только контракт входа, а не сам файл.

```json
{
  "sourceFile": {
    "type": "artifact.file",
    "title": "Исходный файл",
    "required": true
  }
}
```

Ключ `sourceFile` является стабильным машинным именем. Блок
`builtin.file-input` ссылается на него через `config.inputName`.

Для MVP поддерживается один тип входа:

| Тип | Значение при запуске |
| --- | --- |
| `artifact.file` | Идентификатор ранее загруженного файла. |

Содержимое файла, локальный путь пользователя и base64 не сохраняются внутри
описания пайплайна.

## 6. Узел

```json
{
  "id": "read-file",
  "type": "builtin.read-file",
  "typeVersion": 1,
  "title": "Прочитать файл",
  "config": {
    "encoding": "utf-8"
  },
  "ui": {
    "position": {
      "x": 380,
      "y": 160
    }
  }
}
```

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `id` | да | Уникальный идентификатор узла внутри графа. |
| `type` | да | Машинное имя типа узла. |
| `typeVersion` | да | Версия контракта и поведения типа узла. |
| `title` | нет | Пользовательское название конкретного блока. |
| `config` | да | Настройки, зависящие от типа узла. |
| `ui` | нет | Положение и другие данные редактора. |

`id` сохраняется при перемещении и редактировании блока. Новый `id` создаётся
только для нового блока.

Поле `nodeId` в связях и ошибках валидации ссылается на это значение `id`. Это
не отдельный идентификатор и не тип узла.

Пара `type + typeVersion` связывает экземпляр с описанием из каталога. Поле
`config` должно соответствовать `configSchema` этого описания. Поле `title` не
влияет на семантику узла.

## 7. Связь

```json
{
  "id": "edge-read-print",
  "source": {
    "nodeId": "read-file",
    "port": "text"
  },
  "target": {
    "nodeId": "print-text",
    "port": "text"
  }
}
```

Связь одновременно определяет:

- зависимость по порядку выполнения;
- передачу результата из выходного порта в соответствующий входной порт.

Порты типа `control` передают только факт завершения предыдущего узла и не
содержат пользовательских данных.

## 8. Типы узлов MVP

### `builtin.file-input`, версия 1

Назначение: получить файловый артефакт из входов запуска.

Конфигурация:

```json
{
  "inputName": "sourceFile"
}
```

Порты:

| Направление | Порт | Тип данных | Min | Max |
| --- | --- | --- | --- | --- |
| Выход | `file` | `artifact.file` | — | — |

### `builtin.read-file`, версия 1

Назначение: прочитать файловый артефакт и вернуть его содержимое как строку.

Конфигурация:

```json
{
  "encoding": "utf-8"
}
```

Порты:

| Направление | Порт | Тип данных | Min | Max |
| --- | --- | --- | --- | --- |
| Вход | `file` | `artifact.file` | `1` | `1` |
| Выход | `text` | `text` | — | — |

Для MVP единственная поддерживаемая кодировка — `utf-8`.

### `builtin.console-print`, версия 1

Назначение: записать строку в журнал запуска.

Конфигурация:

```json
{
  "prefix": ""
}
```

Порты:

| Направление | Порт | Тип данных | Min | Max |
| --- | --- | --- | --- | --- |
| Вход | `text` | `text` | `1` | `1` |
| Выход | `done` | `control` | — | — |

`prefix` добавляется перед выводимым значением. Поле необязательное, значение
по умолчанию — пустая строка.

### `builtin.end`, версия 1

Назначение: явно обозначить успешное завершение пайплайна.

Конфигурация:

```json
{}
```

Порты:

| Направление | Порт | Тип данных | Min | Max |
| --- | --- | --- | --- | --- |
| Вход | `in` | `control` | `1` | `1` |

Выходных портов нет.

## 9. Конечный блок

Визуальный узел `builtin.end` обязателен. Он явно показывает пользователю точку
успешного завершения процесса и отличает полностью собранный пайплайн от
незаконченного черновика.

Для запуска действуют следующие правила:

- в графе должен быть ровно один узел `builtin.end`;
- у него должна быть хотя бы одна входящая связь;
- исходящие связи для него запрещены;
- пайплайн считается успешно завершённым после выполнения этого узла.

## 10. Визуальные данные

Поле `ui` является частью документа и позволяет восстановить внешний вид
графа.

```json
{
  "position": {
    "x": 380,
    "y": 160
  }
}
```

Правила:

- `ui` не влияет на семантику выполнения;
- отсутствие `ui` не мешает запуску графа;
- координаты не участвуют в вычислении порядка выполнения;
- формат не должен содержать внутренние объекты конкретной UI-библиотеки.

## 11. Черновики и валидация

Определение графа может быть сохранено как черновик, даже если оно ещё не
готово к запуску.

### Сохранение черновика

Для сохранения достаточно структурной корректности:

- документ является валидным JSON;
- поля имеют типы, заданные этим контрактом;
- идентификаторы узлов уникальны внутри графа;
- идентификаторы связей уникальны внутри графа.

Черновик разрешено сохранять с неподключёнными портами, незаполненным `config`,
неизвестным типом узла или без `builtin.end`.

### Готовность к запуску

Для запуска дополнительно требуется:

- каждый `type + typeVersion` существует в выбранной версии каталога;
- `config` каждого узла соответствует его `configSchema`;
- все связи указывают на существующие узлы и порты;
- типы соединённых портов совместимы;
- количество связей соответствует `minConnections` и `maxConnections`;
- граф не содержит циклов;
- в графе присутствует ровно один `builtin.end`;
- каждый узел входит в связный путь, заканчивающийся в `builtin.end`.

### Ошибки валидации

Результат проверки содержит все найденные проблемы:

```json
{
  "valid": false,
  "issues": [
    {
      "code": "MISSING_CONNECTION",
      "message": "Вход file должен иметь одну связь",
      "location": {
        "kind": "port",
        "nodeId": "read-file-2",
        "port": "file"
      }
    }
  ]
}
```

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `valid` | да | Можно ли запустить граф. |
| `issues` | да | Все найденные проблемы; пустой массив для валидного графа. |
| `issues[].code` | да | Стабильный машинный код ошибки. |
| `issues[].message` | да | Человекочитаемое описание. |
| `issues[].location` | да | Место ошибки в графе. |
| `location.kind` | да | `graph`, `node`, `port`, `edge` или `config`. |
| `location.nodeId` | зависит от `kind` | Идентификатор экземпляра узла. |
| `location.edgeId` | зависит от `kind` | Идентификатор связи. |
| `location.port` | зависит от `kind` | Имя порта. |
| `location.configPath` | зависит от `kind` | JSON Pointer внутри `config`, например `/encoding`. |

Тип узла может встречаться в графе несколько раз. Ошибка ссылается на
уникальный `nodeId` экземпляра, поэтому `read-file-1` и `read-file-2`
различаются независимо от общего `type: "builtin.read-file"`.

## 12. Версионирование

Используются три независимых номера версии:

- `schemaVersion` — версия структуры всего документа;
- `nodeCatalogVersion` — версия набора доступных типов узлов;
- `typeVersion` — версия контракта отдельного типа узла.

Примеры:

- добавление нового необязательного поля `ui.color` не меняет поведение узла;
- переименование порта `text` требует новой `typeVersion`;
- изменение структуры `nodes` во всём документе требует новой
  `schemaVersion`.

Документы не преобразуются в новый формат неявно. Результат миграции считается
новым документом с новой версией контракта.
